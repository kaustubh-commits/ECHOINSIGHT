# ADR-0006: Comparison Results as Analysis Contracts

**Status:** Accepted  
**Date:** 2026-07-21

---

## Context

EchoInsight's comparison engine analyzes relationships between songs and structural segments across multiple analytical dimensions.

Unlike `SongDNA` or `SegmentDNA`, comparison results do not describe the state of a single domain object.

Instead, they describe the outcome of applying an analysis algorithm to one or more domain objects.

Examples include:

- song similarity
- segment similarity
- ranking
- dimension-specific scores
- explanatory evidence

The architectural question was:

> Should comparison results be part of the core domain model, or should they belong to the analysis layer that produces them?

This decision affects layer boundaries, dependency direction, and the long-term evolution of analytical algorithms.

---

## Decision Drivers

The decision prioritized:

- Separation of concerns
- Layer independence
- Domain purity
- Extensibility
- Clear dependency direction

---

## Decision

Comparison results are implemented as **analysis contracts**, not domain objects.

They belong to the comparison subsystem that produces them and therefore reside in:

```text
src.analysis.comparison.contracts
```

The dependency direction is intentionally one-way.

```text
┌─────────────────────────────┐
│        src.core             │
│  SongDNA                    │
│  StructureDNA               │
│  SegmentDNA                 │
└──────────────┬──────────────┘
               │
               ▼
┌─────────────────────────────┐
│      src.analysis           │
│  Comparison Engine          │
│  Comparison Contracts       │
└─────────────────────────────┘
```

The domain model has no knowledge of comparison.

Comparison engines consume domain objects and produce comparison contracts describing the outcome of analysis.

These contracts define the public interface between the comparison subsystem and its consumers.

---

## Alternatives Considered

### Domain-Level Comparison Types

Place comparison result objects alongside `SongDNA` and other domain types.

**Rejected because**

Comparison is not an intrinsic property of a song.

A song exists independently of whether it is ever compared to another song.

Embedding comparison concepts into the domain would introduce algorithm-specific concerns into the core model and weaken the separation between domain representation and analytical services.

---

### Persist Comparison Results on SongDNA

Store similarity relationships directly inside the aggregate.

**Rejected because**

Comparison results describe relationships between multiple domain objects rather than attributes of a single object.

Persisting these relationships inside `SongDNA` would introduce synchronization problems whenever either song changes.

Comparison is a derived artifact, not domain state.

---

### Unstructured Data Transfer

Return dictionaries or loosely structured JSON objects instead of typed contracts.

**Rejected because**

Unstructured outputs sacrifice type safety, discoverability, validation, and clear API contracts.

Consumers become responsible for understanding implementation details rather than interacting with a well-defined interface.

Strongly typed contracts provide a significantly more maintainable integration boundary.

---

## Consequences

### Advantages

- The domain model remains independent of analytical algorithms.
- Comparison contracts can evolve without modifying the core domain.
- Dependency direction remains consistent throughout the architecture.
- Consumers interact with stable, well-defined result types.
- Multiple comparison implementations can share the same public contract.

### Disadvantages

- Additional contract types must be maintained.
- Consumers import comparison contracts separately from the domain model.
- Some information is intentionally duplicated to create self-contained result objects.

### Tradeoffs

EchoInsight treats analytical results as products of services rather than properties of domain objects.

Maintaining this separation slightly increases the number of types in the system but produces significantly cleaner architectural boundaries and allows analytical algorithms to evolve independently of the core domain model.

---

## Future Considerations

Other analytical subsystems should follow the same architectural pattern.

Recommendation engines, clustering algorithms, embedding pipelines, and future analytical components should define their own contracts within their respective analysis packages rather than extending the domain model.

The guiding principle is:

> The domain describes what a song **is**. Analysis contracts describe what analytical processes **produce**.
