# ADR-0002: Immutable Domain Model

**Status:** Accepted  
**Date:** 2026-07-21

---

## Context

EchoInsight's domain objects represent observations produced by deterministic analysis.

Given identical audio and identical extraction settings, the analysis should produce identical domain objects.

These objects represent facts that have already been measured rather than entities that evolve over time.

The architectural question was:

> Should domain objects be mutable or immutable?

The answer influences correctness, thread safety, testing, serialization, caching, and the overall complexity of the system.

---

## Decision Drivers

The decision prioritized:

- Correctness
- Deterministic behaviour
- Thread safety
- Simplicity
- Predictable serialization
- Long-term maintainability

---

## Decision

All domain objects are implemented as immutable (`frozen=True`) dataclasses.

Once constructed, a domain object cannot be modified.

Any change requires constructing a new object rather than mutating an existing one.

This models the domain accurately.

A completed analysis is a historical fact.

Changing the value of an extracted tempo or segment boundary after construction would no longer represent the same analysis.

Immutability therefore aligns the software model with the problem domain.

---

## Alternatives Considered

### Mutable dataclasses

Standard Python dataclasses allow fields to change after construction.

**Rejected because**

Mutable objects introduce temporal coupling.

An object's validity depends on *when* it is observed rather than solely on its construction.

This increases cognitive complexity, makes reasoning about shared state harder, and creates opportunities for subtle bugs when objects are reused across different consumers.

---

### Pydantic models

Pydantic offers validation, serialization, and optional immutability.

**Rejected because**

The domain layer intentionally depends only on the Python standard library.

Introducing Pydantic would violate this architectural boundary by introducing an external dependency into the core domain.

The domain requires only lightweight structural validation that is adequately handled by dataclasses.

---

### NamedTuple

NamedTuple provides lightweight immutable containers.

**Rejected because**

NamedTuple lacks capabilities required by EchoInsight's domain model, including `__post_init__` validation, default factories, inheritance, and the expressiveness needed for complex nested structures.

---

## Consequences

### Advantages

- Eliminates accidental mutation
- Encourages deterministic behaviour
- Safe to share between threads
- Predictable serialization
- Simpler reasoning throughout the system
- Supports hashing when contained fields are themselves hashable

### Disadvantages

- Updating a value requires constructing a replacement object.
- Nested structures require careful use of immutable collection types.

### Tradeoffs

The additional allocation cost of constructing replacement objects is negligible compared to audio analysis itself.

The gains in correctness, maintainability, and reasoning significantly outweigh the small construction overhead.

---

## Future Considerations

If profiling ever demonstrates that domain object construction becomes a measurable bottleneck, optimization should be driven by evidence rather than assumption.

Potential optimizations include:

- `__slots__`
- custom constructors
- specialized serialization paths

The architectural commitment to immutability should remain unchanged unless the underlying domain itself changes.
