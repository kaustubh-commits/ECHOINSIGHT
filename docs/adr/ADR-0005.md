# ADR-0005: Validation as a Domain Responsibility

**Status:** Accepted  
**Date:** 2026-07-21

---

## Context

EchoInsight's domain model represents deterministic measurements derived from audio analysis.

Once a domain object has been constructed, every consumer should be able to assume that it satisfies the invariants required by the model.

Examples include:

- temporal consistency
- valid confidence ranges
- structurally complete feature vectors
- ownership consistency
- aggregate integrity

The architectural question was:

> Should validation be the responsibility of the domain model itself, or should it be delegated to external validators or application services?

This decision affects correctness, encapsulation, testing, and the reliability of every downstream component.

---

## Decision Drivers

The decision prioritized:

- Correctness by construction
- Fail-fast behaviour
- Encapsulation
- Deterministic execution
- Simplicity
- Long-term maintainability

---

## Decision

Validation is a responsibility of the domain model.

Every domain object validates its own invariants during construction using `__post_init__`.

Construction either succeeds with a valid object or fails immediately with an exception.

No domain object may exist in a partially valid state.

Validation is intentionally divided into two categories.

### Structural Validation

Structural validation verifies properties that depend only on the object being constructed.

Typical examples include:

- numeric ranges
- tuple lengths
- required fields
- temporal ordering
- enum correctness

Structural validation is local, deterministic, and inexpensive.

---

### Aggregate Validation

Aggregate validation verifies relationships between an object and the objects it owns.

Examples include:

- contiguous segment ordering
- ownership consistency
- duration consistency
- structural invariants spanning multiple child objects

These validations remain part of object construction because they define the correctness of the aggregate itself.

The guiding principle is:

> Every successfully constructed domain object satisfies all invariants that define its correctness.

---

## Alternatives Considered

### External Validator Classes

Validation is implemented separately from the domain model.

Examples:

- `SongDNAValidator`
- `StructureDNAValidator`

**Rejected because**

Separating validation from the model creates two independent sources of truth.

Consumers may accidentally construct invalid objects without invoking validation.

Responsibility becomes fragmented between the data structure and an external service.

The model no longer guarantees its own correctness.

---

### Deferred Validation

Objects are created immediately and validated later.

**Rejected because**

Deferred validation allows invalid domain objects to circulate throughout the system.

Failures occur farther from their origin, making debugging significantly more difficult.

This approach also complicates testing because every consumer must account for partially valid objects.

---

### Schema-Based Validation

Validation rules are defined in an external schema such as JSON Schema or Pydantic.

**Rejected because**

The domain layer intentionally depends only on the Python standard library.

Maintaining validation rules outside the domain model introduces duplication and increases the likelihood of implementation drift between the schema and the code.

---

## Consequences

### Advantages

- Every constructed domain object is guaranteed to satisfy its invariants.
- Invalid data is rejected immediately.
- Validation logic remains colocated with the data it protects.
- Consumers never need to remember to invoke validation manually.
- Testing becomes straightforward because invalid construction paths can be exercised directly.

### Disadvantages

- Construction performs additional work.
- Aggregate validation may require iterating over owned collections.
- Validation errors can only describe information available during construction.

### Tradeoffs

EchoInsight accepts a small construction cost in exchange for significantly stronger correctness guarantees.

Audio analysis dominates runtime by several orders of magnitude, making validation overhead negligible for the expected workload.

Correctness and developer confidence are considered substantially more valuable than the small performance cost of eager validation.

---

## Future Considerations

If EchoInsight later supports interactive editing of analyses, such as manually adjusting segment boundaries or modifying structural annotations, additional validation mechanisms may become appropriate.

These should complement, rather than replace, construction-time validation.

The fundamental principle remains unchanged:

> A completed domain object should never exist in an invalid state.
